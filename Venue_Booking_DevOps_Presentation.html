VRBS · DevOps Lab Viva 02
01 · CONTEXT & MOTIVATION

The Problem: Manual Resource Allocation Chaos

Why traditional paper ledgers and fragmented email trails break down in modern educational campuses

CAMPUS BOTTLENECK

The High Cost of Uncoordinated Venue Scheduling

  • High Resource Contention: 15+ academic departments, clubs, and student bodies competing for limited halls.
  • Fragmented Communication: Booking requests dispatched over personal emails, WhatsApp chats, and paper registers.
  • Zero Concurrency Locks: Two coordinators can reserve the exact same hall at the same time without knowing.
  • Deployment Fragility: Legacy institutional apps updated manually via FTP or direct server edits, causing outages.
Direct Consequence
Embarrassing double-booking incidents during university events, wasted facilities, and constant administrative friction.
1. Double-Booking Collisions

Without an atomic database constraint, simultaneous verbal approvals result in duplicate occupancy for high-demand halls like the Main Auditorium.

2. Absence of Centralised Audit Trail

No verifiable digital history of who approved a venue, what time slot was locked, or whether cancellations were released back to the general pool.

3. Rigid, Inflexible Time Blocks

Legacy systems forced fixed 3-hour chunks (e.g. 09:00–12:00, 13:00–16:00), making it impossible to schedule a 45-minute guest lecture or viva session.

4. Configuration Drift & Manual Outages

Manual server patching causes "works on my machine" defects, unversioned dependencies, and downtime during critical college examination weeks.

02 · CORE INNOVATION

Dynamic Booking Engine (08:00 – 20:00)

Eliminating rigid 3-hour fixed blocks with arbitrary slot reservation and instant collision prevention

VRBS · Dynamic Booking & Schedule Picker (Live Application Screenshot)
Figure 5.1: Actual Dynamic Booking UI — Real-time 08:00–20:00 schedule matrix displaying Confirmed slots and immediate conflict alert modal.
1. Arbitrary Time Window Flexibility

Users choose exact start and end times (e.g. 09:30 to 11:15 or 14:00 to 16:30) within the campus operational window (08:00 to 20:00), maximizing room utilization.

2. Sub-Second Overlap Detection Algorithm

Mathematical collision check: (newStart < existingEnd) AND (newEnd > existingStart). Prevents identical, partial, or superset overlaps at the database tier.

3. Instant Visual Conflict Feedback

Schedule matrix provides color-coded status badges (Confirmed, Pending, Available) and blocks conflicting submissions before form dispatch.

4. Concurrency & Integrity Enforcement

Transactions wrapped in @Transactional(isolation = SERIALIZABLE) to guarantee zero race conditions even under concurrent rush during fest registrations.

02 · APPLICATION ARCHITECTURE

Layered Architecture & Booking Lifecycle

Clean separation of concerns with deterministic state transitions and transactional safety

1. Presentation Layer (Thymeleaf & Bootstrap 5)

Dynamic HTML5 templates, JavaScript time-slot matrix, CSRF token binding, and responsive layout.

2. Controller & Security Layer (Spring MVC)

REST & View controllers, @Valid DTO input validation, role-based URL guards, and global exception interception.

3. Business Service Layer (Spring Service)

BookingService, ConflictEngine, and VenueService enforcing invariants inside ACID transactional boundaries.

4. Persistence Layer (Spring Data JPA / MySQL 8.0)

Hibernate ORM mapping, indexed foreign keys, relational integrity, and connection pooling via HikariCP.

FINITE STATE MACHINE

Booking State Machine

1. DRAFT / REQUESTED
Requester specifies venue, date, and 08:00–20:00 time. Conflict engine confirms zero collisions.
2. PENDING APPROVAL
Slot temporarily held; routed to Admin / Authority dashboard for compliance review.
3. APPROVED / CONFIRMED
Administrator one-click approval locks slot permanently; booking confirmation dispatched.
4. COMPLETED / CANCELLED
Event concludes or user cancels; atomic trigger releases slot back into the available pool.

VRBS · DevOps Lab Viva 11
04 · SHIFT-LEFT DEFECT PREVENTION

The Quality Gate: Preventing Broken Builds from Shipping

Automated pipeline failure halting artifact creation when defects or test failures occur

1. Immediate Fail-Fast Trigger

If even a single unit test or dynamic conflict validation fails, Maven exits with error code 1, immediately terminating the Jenkins job.

2. Zero Bad Artifacts Generated

Downstream stages (WAR packaging, Docker build, Docker Hub push, and Ansible deployment) are completely skipped. Broken code NEVER reaches registry.

3. Instant Developer Blame & Feedback

Jenkins captures failure stack traces and immediately identifies the faulty commit SHA, allowing developers to rectify bugs within minutes.

4. Production Stability Protected

Guarantees that the running container on the server remains untouched and fully operational while defects are isolated in CI.

05 · CONTAINERISATION

Containerisation with Docker: Portable & Reproducible

Multi-stage container builds ensuring minimal footprint, enhanced security, and environment parity

Multi-Stage Production Dockerfile
# Runtime Stage
FROM eclipse-temurin:17-jre-jammy
RUN useradd -u 1001 -m -s /bin/bash appuser
WORKDIR /opt/vrbs
COPY --chown=appuser:appuser target/*.war app.war
USER appuser
EXPOSE 8080
HEALTHCHECK --interval=15s --timeout=5s --retries=3 \
  CMD curl -f http://localhost:8080/actuator/health || exit 1
ENTRYPOINT ["java", "-jar", "app.war"]
Container Hardening Practices
  • Non-Root Execution: Runs as appuser (UID 1001) to prevent root escalation vulnerabilities.
  • Minimal Attack Surface: JRE-only base image reduces vulnerabilities from ~400 down to near zero.
  • Native Healthchecks: Docker engine automatically tracks container readiness state.

VRBS · DevOps Lab Viva 16
06 · ENGINEERING REFLECTION

Challenges Overcome & Key Technical Learnings

Real-world engineering hurdles solved through DevOps principles and automated feedback loops

TECHNICAL OBSTACLES
Challenges Encountered & Solutions
1. Concurrency Race Conditions

Simultaneous submissions caused duplicate bookings.
Solution: Enforced database-level pessimistic locking and mathematical overlap queries inside @Transactional boundaries.

2. CI/CD Environment Inconsistencies

Tests passed on Windows development machine but failed in CI.
Solution: Standardised Eclipse Temurin 17 JRE Docker image matching exact production target.

3. Flaky Headless Selenium Tests

Dynamic DOM elements caused intermittent stale element errors.
Solution: Replaced hardcoded sleep with explicit WebDriverWait ExpectedConditions.

DEVOPS PHILOSOPHY
Core DevOps Insights Acquired
1. Shift-Left Defect Prevention

Catching bugs in unit testing costs <10% of fixing them post-deployment. Quality Gates make releases stress-free.

2. Immutable Container Infrastructure

Deploying immutable Docker images prevents snowflake servers and guarantees identical runtime behavior.

3. Idempotent Infrastructure as Code

Ansible playbooks act as living, executable documentation that eliminates human configuration error.

4. Automated Health-Gated Rollback

Automated health checks paired with rollback playbooks eliminate fear of breaking production.
